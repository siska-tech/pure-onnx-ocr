# タスク概要
認識モデル（SVTR）のどの演算子が遅いのかを特定する。

[benchmark-openvino-throughput](benchmark-openvino-throughput.md) では、複数画像を処理すると本クレートは CPU をほぼ使い切っていた。そのため、これ以上速くするには、1 枚あたりの CPU 時間を減らす必要がある。修正版の tract（task-perf-006）でも、処理時間の大半は認識が占めている。

## 結果（要点）

- **認識の 1 スレッドでの差が、OpenVINO との差の大部分を説明する**。
  - 修正版の tract の認識モデル単体（`[1,3,48,320]`、1 スレッド）は、OpenVINO（1 スレッド、[benchmark-openvino](benchmark-openvino.md)）の 1.34 倍（tiny）、1.33 倍（small）、1.10 倍（medium）の時間だった。
  - 複数画像の計測での 1 枚あたりの CPU 時間（平均使用コア数 ÷ スループット）の比も、1.50 倍、1.33 倍、1.11 倍で、ほぼ同じだった。
- **認識の時間の 66〜80% は行列演算（`OptMatMul`）である**。1x1 畳み込みと全結合層である。
  - 大きい行列演算は、1 スレッドで 68〜91 GFLOP/s 出ている。i7-1360P の P コアの理論性能（AVX2 + FMA、約 150 GFLOP/s）の 5〜6 割で、カーネル自体の効率は悪くない。
  - 効率が低いのは、**最後の CTC の全結合層**（出力 40 × 辞書の大きさ、k = 80〜120）で、40〜48 GFLOP/s にとどまる。small では認識の 9%、tiny では 13% を占める。`M`（時間ステップ数 40）と `k` が小さい形である。
- 行列演算の入力のパック（`OptMatMulPack`）が 8〜11% を占める。行列演算ごとに、活性化を詰め直している。
- depthwise 畳み込みは、修正版の tract で 4〜6% まで縮んだ（tract 0.23.8 では 13〜22%）。
- **本クレート側で減らせる部分はほとんどない**。残りは tract の行列演算（小さい形の効率とパック）の問題である。

## 計測条件

- ツール: [tools/tract-profile](../../../tools/tract-profile/README.md)。入力は `[1,3,48,320]`（幅 320 は、ほとんどの行の幅である最小幅）、合成値。2 回のウォームアップの後、20 回の平均。
- スレッド数は 1。パイプラインの中では、認識はバッチごとにシングルスレッドで動くためである（task-perf-001）。
- tract 0.23.8 と、修正版の tract（task-perf-006 の worktree）。PC は i7-1360P。

## 演算子ごとの時間（ミリ秒、1 スレッド、tract 0.23.8 → 修正版）

| 演算子 | tiny | small | medium |
| :--- | ---: | ---: | ---: |
| `OptMatMul`（1x1 畳み込み、全結合層など） | 5.0 → 5.7 | 29.9 → 29.2 | 137.0 → 131.5 |
| `OptMatMulPack`（入力のパック） | 1.0 → 0.9 | 3.8 → 3.5 | 12.0 → 12.6 |
| `DepthWiseConv` | 2.0 → 0.5 | 8.6 → 1.7 | 23.9 → 4.6 |
| `GeluExact` | 0.3 → 0.4 | 1.2 → 1.3 | 4.0 → 3.8 |
| 合計（ノードの合計） | 9.3 → 8.6 | 51.0 → 42.8 | 186.4 → 163.7 |

修正版で `DirectSpatialConv`（tiny 0.2、small 2.7、medium 4.3 ms）が現れるのは、tract main で一部の畳み込みの実装が変わったためである。

## 判断（次にやること）

1. **本クレート側の対策は見送る**。重いのは tract の行列演算そのもので、グラフの書き換えなどで減らせる部分はない。
2. tract に提案できる候補（どれも upstream での作業になり、規模が大きい）:
   - **小さい `k` と `M` の行列演算の効率**: CTC の全結合層（40 × 数千〜1.9 万、k = 80〜120）。出力の向きを変える（`N` 方向にタイルを取る）、または小さい `k` 向けのカーネルを選べるようにする。
   - **パックの削減**: 1x1 畳み込みが続く部分で、前の演算の出力をパック済みの配置で書く、または小さい行列ではパックせずに読むカーネルを使う。
3. 優先度は低い。複数画像のスループットは、修正版の tract で OpenVINO の 79〜99% に達している。上記の改善で詰められるのは、tiny と small の残り 2 割程度である。まず task-perf-006 の 3 つの PR の結果を見てから判断する。
