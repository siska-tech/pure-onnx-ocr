# タスク概要
既定の推論スレッド数を「論理 CPU 数、最大 8」から「論理 CPU 数、最大 16」に引き上げる。

## 背景
[benchmark-openvino](benchmark-openvino.md) の追加計測（v6 small、交互に 3 ラウンド、ミリ秒）:

| スレッド数 | 合計（搭乗券 / 日本語） | rec 推論 | det 推論 | 平均使用コア数 |
|---:|---:|---:|---:|---:|
| 8（既定） | 1,389 / 1,529 | 746 / 834 | 572 / 562 | 4.3 |
| 12 | 1,404 / 1,502 | 714 / 734 | 614 / 630 | 5.6 |
| 16 | 1,256 / 1,284 | 636 / 608 | 577 / 570 | 6.3 |

- 16 スレッドで、認識が 15〜27% 速くなり、合計は 10〜16% 縮んだ。検出は変わらない。
- task-perf-001 の「8 と 16 で差がない」は、行列演算の並列化だけを計測した結果だった。認識のバッチを並列に実行する現在の実装では、16 スレッドにも効果がある。

## 要件
- `src/threading.rs` の `default_inference_threads()` の上限を 16 にし、ドキュメントコメントの根拠を更新する。
- v6 tiny / small / medium と v5 mobile / server で、8 と 16 を交互に計測する。合計の時間、スレッド数、メモリのピークを記録する。
- 可能なら、論理 CPU が 8 以下の環境と、ハイブリッドでない CPU でも、悪化しないことを確かめる。
- 既定の動作が変わるので、CHANGELOG に記載する。task-perf-001 の「4. スレッド数の既定値」に、結論を修正したことを追記する。

## 完了の条件
- 上の計測で、どのモデルでも合計の時間が悪化しない。
- 出力が変わらない（`thread_count_does_not_change_results` を含む全テストが成功する）。

## 結果（要点）

変更前（上限 8）と変更後（上限 16）を交互に 3 ラウンド実行した（`run_bench.py --baseline-exe`、i7-1360P、ウォームアップ後の中央値、ミリ秒）。

| Model | 画像 | 変更前 | 変更後 | 倍率 | det 推論 | rec 推論 | 初回 |
|---|---|---:|---:|---:|---:|---:|---:|
| v6 tiny | 搭乗券 | 436 | 417 | 0.96 | 0.99 | 0.88 | 1.09 |
| v6 tiny | 日本語 | 492 | 435 | 0.88 | 0.94 | 0.74 | 0.99 |
| v6 small | 搭乗券 | 1,144 | 1,080 | 0.94 | 1.01 | 0.91 | 1.05 |
| v6 small | 日本語 | 1,276 | 1,139 | 0.89 | 0.98 | 0.82 | 0.93 |
| v6 medium | 搭乗券 | 4,349 | 4,081 | 0.94 | 1.00 | 0.90 | 1.12 |
| v6 medium | 日本語 | 5,187 | 4,641 | 0.89 | 0.94 | 0.88 | 0.94 |
| v5 mobile | 搭乗券 | 1,293 | 1,257 | 0.97 | 1.11 | 0.94 | 1.05 |
| v5 mobile | 日本語 | 1,264 | 1,216 | 0.96 | 1.03 | 0.90 | 0.97 |
| v5 server | 搭乗券 | 10,967 | 9,559 | 0.87 | 0.97 | 0.83 | 0.95 |
| v5 server | 日本語 | 12,222 | 10,041 | 0.82 | 0.96 | 0.75 | 0.85 |

倍率の列は、変更前に対する比（1 未満が速い）。

- **合計の時間は、全モデル・全画像で 3〜18% 縮んだ**。悪化したものはない。
  - 縮んだのは認識の推論（6〜26%）で、検出の推論は変わらない（ばらつきの範囲）。
  - 予想どおり、認識の比率が大きい v5 server と、切り出しの多い日本語の画像で効果が大きい。
- **出力は完全に一致した**（全モデル・全画像で、領域数、文字列、box の座標）。
- 初回の実行は −15〜+12% で、一定の傾向はない。

### メモリとスレッド数

| Model | Private のピーク（変更前 → 変更後） | 実行後の Private（変更前 → 変更後） | スレッド数 | 平均使用コア数 |
|---|---:|---:|---:|---:|
| v6 tiny | 150 → 158 MB | 75 → 82 MB | 28 → 36 | 3.0 → 4.3 |
| v6 small | 405 → 502 MB | 224 → 234 MB | 28 → 36 | 4.3 → 6.6 |
| v6 medium | 1,043 → 1,575 MB | 842 → 847 MB | 25 → 33 | 4.8 → 7.8 |
| v5 mobile | 341 → 407 MB | 176 → 186 MB | 28 → 36 | 4.8 → 7.7 |
| v5 server | 1,398 → 1,873 MB | 約 1,010 → 約 1,030 MB | 25 → 33 | 5.5 → 9.2 |

- **メモリのピークは増えたが、増えるのは初回の実行の間だけ**である。パイプラインを実行し終えた後のメモリは、変更前とほぼ同じか、数 % 多いだけだった。
  - 原因: 初回は、認識の推論計画を最大 16 個同時にコンパイルする。コンパイル中は、モデルの複製と最適化の途中の状態を一時的に持つので、同時に動くコンパイルの数に比例してピークが上がる。また、同じ幅の計画を複数のスレッドが重複してコンパイルすることもある（`runnable_for_dims` は、ロックの外でコンパイルしている）。
  - 対策は [task-perf-007](task-perf-007-warmup.md) で行う（同時にコンパイルする数の制限と、重複の排除）。
  - **追記（2026-10-07）**: task-perf-007 で重複コンパイルをなくし、ピークは上限 8 のときの水準に戻った（v6 medium 1,575 → 1,045 MB）。
  - v6 medium のピーク 1.6 GB は、OpenVINO の Private のピーク（1.8 GB、[benchmark-openvino](benchmark-openvino.md)）よりはまだ小さい。

## 判断

- 完了の条件（合計の時間が悪化しない、出力が変わらない）を満たしたので、既定値を「論理 CPU 数、最大 16」に変更した。
- 論理 CPU が 8 以下の環境では、既定値は変わらない（`clamp(1, 16)` でも同じ値になる）。そのため、計画で挙げた「8 以下の環境での確認」は不要になった。
- 論理 CPU が 9 以上で、ハイブリッドでない CPU では未確認である。
