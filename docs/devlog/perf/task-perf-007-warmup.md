# タスク概要
よく使う形の推論計画を事前にコンパイルする API を追加し、初回の実行を速くする。

## 背景
[benchmark-openvino](benchmark-openvino.md) より:

- 本クレートは、入力の形ごとに推論計画をコンパイルする。そのため読み込みは OpenVINO より 5〜10 倍速いが、初回の実行は遅い。
  - 初回とウォームアップ後の差: small 0.9 秒、medium 1.9 秒、tiny 0.5 秒。
  - 認識は幅ごとに計画を作るので、新しい幅の切り出しが来るたびにコンパイルが起きる。
- 読み込みから初回の結果が出るまでの時間は、OpenVINO の 1.5〜2.1 倍だった。

## 要件
- 推論計画のコンパイルを、同時に動く数を制限し、同じ形の計画を複数のスレッドが重複してコンパイルしないようにする（single-flight）。[task-perf-003](task-perf-003-default-threads.md) で既定のスレッド数を 16 にしてから、初回の実行中のメモリのピークが増えた（v6 medium で 1,043 → 1,575 MB。実行後のメモリは変わらない）。これは warmup を呼ばない場合にも効く。
- `OcrEngine::warmup(...)`（名前は要検討）を追加する。認識の幅（32 刻みで、よく出る範囲）と、検出の形（例: 指定した画像サイズから求めた形）の推論計画を、スレッドプールで並列にコンパイルしてキャッシュに入れる。
- 事前にコンパイルする数は、計画のキャッシュの容量（認識は既定で 16）を超えないようにする。
- 既定の動作は変えない（呼び出した場合だけ動く）。バックグラウンドで実行する版は、必要があれば別に検討する。
- 推論計画が同じなので、出力は変わらない。

## 計測
- 読み込み + warmup + 初回の時間と、warmup なしの読み込み + 初回の時間を比べる。
- メモリのピークの増え方を記録する（medium では、計画のキャッシュで約 1 GB を使っている）。

## 結果（要点）

### 1. 同じ形の推論計画の重複コンパイルをなくした（single-flight）

- **原因**: 認識の切り出しは、ほとんどが最小幅の 320 に切り上げられる。キャッシュが空の状態では、並列に動くバッチがすべて幅 320 の計画を見つけられず、それぞれがコンパイルしていた。
  - v6 small の初回の実行で、認識の計画を 17 回コンパイルしていたが、幅は搭乗券で 5 種類、日本語で 2 種類しかなかった。幅 320 だけで 13〜16 回コンパイルしていた。
- **対策**: `SharedPlanCache`（`src/onnx_model.rs`）を追加し、検出・認識・向きの分類器のセッションで使うようにした。
  - 最初のスレッドだけがコンパイルし、同じ形を必要とするほかのスレッドは完了を待って、その計画を使う。
  - 違う形の計画は、今までどおり並列にコンパイルする。コンパイル中はロックを持たない。
  - コンパイルが失敗した場合や panic した場合も、待っているスレッドを起こす。失敗した場合は、待っていたスレッドがコンパイルし直す。
- コンパイルの回数は、搭乗券で 17 → 5 回、日本語で 17 → 2 回になった。

task-perf-003 の状態（上限 16）を基準に、交互に 3 ラウンド計測した（1 枚目の画像＝搭乗券の初回、ミリ秒）。

| Model | 初回（変更前 → 変更後） | Private のピーク（変更前 → 変更後） | 参考: 上限 8 のときのピーク |
| :--- | ---: | ---: | ---: |
| v6 tiny | 966 → 744（0.77） | 161 → 154 MB | 150 MB |
| v6 small | 2,190 → 1,897（0.87） | 503 → 409 MB | 405 MB |
| v6 medium | 6,072 → 5,459（0.90） | 1,575 → 1,045 MB | 1,043 MB |
| v5 mobile | 2,443 → 2,107（0.86） | 405 → 346 MB | 341 MB |
| v5 server | 14,394 → 11,936（0.83） | 1,857 → 1,403 MB | 1,398 MB |

- **メモリのピークは、task-perf-003 の前（上限 8）の水準に戻った**。
- **1 枚目の画像の初回の実行は 10〜23% 縮んだ**。2 枚目の画像（日本語）の初回は、幅 320 の計画がすでにあるので、−7〜+9% で差はばらつきの範囲だった。
- ウォームアップ後の時間は変わらない（0.95〜1.02 倍）。出力は完全に一致した。
- 重複がなくなると、同時に動くコンパイルは画像あたり 2〜5 個になる。メモリのピークも戻ったので、**同時に動くコンパイルの数の制限は入れなかった**。

### 2. `OcrEngine::warmup(width, height)` を追加した

- 次の推論計画を、エンジンのスレッドプールで並列にコンパイルする。
  - 指定した画像サイズの検出の計画
  - 最小幅（320）の認識の計画（バッチサイズは `rec_batch_size`）
  - 向きの分類器の計画（設定されている場合）
- それより広い行、ほかの画像サイズ、90° / 270° 回転したページの計画は、今までどおり初回の使用時にコンパイルする。
- 同じ計画を使うので、出力は変わらない。

同じビルドで `warmup` あり／なしを交互に 3 ラウンド計測した（搭乗券、ミリ秒）。

| Model | warmup | 初回（なし → あり） | 読み込み + warmup + 初回（なし → あり） |
| :--- | ---: | ---: | ---: |
| v6 tiny | 259 | 817 → 546（0.67） | 852 → 840 |
| v6 small | 306 | 1,857 → 1,372（0.74） | 1,928 → 1,751 |
| v6 medium | 660 | 5,451 → 4,572（0.84） | 5,651 → 5,448 |

- warmup した画像サイズでは、**初回の実行が 16〜33% 縮む**。
- 読み込みから初回の結果までの合計も、変わらないか少し縮む。コンパイルを並列に行うためである。サーバーの起動時などに呼んでおけば、最初のリクエストが速くなる。
- small で warmup した後も、初回はウォームアップ後より約 250 ms 遅い。残りは、広い行（352、512、704、1440）の計画のコンパイルである。

### 計画時の見込みとの比較

- 計画では「初回 −0.5〜1.9 秒」と見込んでいた。task-perf-003 の状態からの実際の短縮は、single-flight と warmup を合わせて、small 2.19 → 1.37 秒（−0.8 秒）、medium 6.07 → 4.57 秒（−1.5 秒）だった。
- 読み込み + 初回では、OpenVINO（small 1.41 秒、medium 3.43 秒、[benchmark-openvino](benchmark-openvino.md)）に対して、small 1.75 秒、medium 5.45 秒である。medium の差は、主にウォームアップ後の推論そのものの差（task-perf-006 の対象）である。
