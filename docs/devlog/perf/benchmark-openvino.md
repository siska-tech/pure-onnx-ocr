# pure-onnx-ocr と OpenVINO の CPU 推論性能比較（同一 PC・同一 ONNX）

[benchmark-v5-vs-v6](../ppocrv6/benchmark-v5-vs-v6.md) では、OpenVINO との比較に公式の数値を使っていた。公式の数値は Xeon で計測したもので、画像も違う。本書では、**同じ PC、同じ画像、同じ ONNX ファイル、同じ前処理と後処理**で OpenVINO Runtime を実際に動かし、本クレートとの差を測った。

計測ツールは [tools/openvino-bench](../../../tools/openvino-bench/README.md)、集計結果は [tools/openvino-bench/results/summary.md](../../../tools/openvino-bench/results/summary.md) にある（プロセスごとの生データは容量が大きいので、リポジトリには含めていない）。

## 要点

ウォームアップ後の処理時間（中央値）。OpenVINO は最も速い設定（`ov`）の値である。

| Model | 画像 | pure-onnx-ocr | OpenVINO | Ratio（pure / OV） |
|---|---|---:|---:|---:|
| v6 small | general_ocr_002.jpg | 1.37 s | 0.58 s | **2.35** |
| v6 small | ja.jpg | 1.54 s | 0.79 s | 1.94 |
| v6 medium | general_ocr_002.jpg | 4.99 s | 2.47 s | **2.02** |
| v6 medium | ja.jpg | 5.80 s | 3.23 s | 1.80 |
| v6 tiny | general_ocr_002.jpg | 0.49 s | 0.18 s | 2.70 |
| v6 tiny | ja.jpg | 0.55 s | 0.25 s | 2.18 |

- **本クレートは、OpenVINO の 1.8〜2.7 倍の時間がかかる**。速度にすると OpenVINO の約 37〜56%。
  - small と medium では、2 画像の平均で 2.11 倍と 1.89 倍だった。
  - 公式の数値との比較から見積もっていた「2〜3 倍」は、実測でもほぼそのとおりだった。
- OpenVINO を素朴な設定（`LATENCY`、切り出しを 1 枚ずつ推論）で使った場合と比べると、差は **1.38〜1.49 倍** に縮む。
- **差の 6〜9 割は検出（DBNet）の推論から来ている**。
  - 検出モデル単体では、本クレートは 5〜8 倍遅い。
  - 認識モデル単体（バッチ 1）では 1.7〜2.8 倍にとどまる。そのうえ、パイプラインでは認識をバッチ単位で並列に実行しているので、認識の差は 1.3〜1.9 倍まで縮んでいる。
- 本クレートが勝っている項目もある。
  - **メモリ**: Private Bytes のピークが、OpenVINO の 27〜58%。
  - **スレッド数**: 25〜28 本。OpenVINO は 45〜50 本。
  - **読み込み時間**: 40〜245 ms。OpenVINO は 450〜860 ms。
  - ただし、初回の実行に推論計画のコンパイルが入る。そのため、読み込みから初回の結果が出るまでの時間は、OpenVINO の 1.5〜2.1 倍になる。
- **出力は完全に一致した**。全モデル・全画像で、領域数、文字列、box の座標が同じだった。前処理と後処理が同一であることの裏付けになる。

### OpenVINO 側の公平性

- **前処理と後処理は、本クレートのコードそのもの**である。OpenVINO 側のパイプラインは `OcrEngine::run_with_metrics_from_image_impl` を写したもので、`DetInferenceSession::run` と `RecInferenceSession::run` の 2 か所だけを OpenVINO の infer request に置き換えている。
  - 使っている公開 API: `DetPreProcessor`、`DetPostProcessor::db_boxes`、`min_area_quad` + `crop_quad`、`RecPreProcessor`、`RecPostProcessor`
  - Python は使っていないので、前処理と後処理の言語差もない。
- 設定は `inference.yml` から `OcrEngineBuilder::build` と同じ手順で作る。pure 側のプロセスが毎回 `engine.config()` との一致を確かめ、すべての実行で一致した。
- 認識の並列化も、本クレートと同じ構造にそろえた。認識のスイープは下の「OpenVINO の設定の選び方」を参照。
  - 本クレート: rayon で複数のバッチを並列に実行する。
  - OpenVINO: `THROUGHPUT` ヒントで 4 ストリーム・4 request を使い、切り出しを並列に流す。
  - 前処理の並列化には、どちらも同じ 8 スレッドの rayon プールを使う。
- OpenVINO の推論時間には、入力テンソルを OpenVINO のテンソルへコピーする時間と、出力を ndarray へコピーする時間を含めた。本クレート側も、入力テンソルを `clone` する時間を含んでいる。

### OpenVINO の設定の選び方（事前スイープ、3 回の中央値）

v6 small のパイプライン全体（ミリ秒、搭乗券 / 日本語）。

| 認識の設定 | small | medium |
| :--- | ---: | ---: |
| LATENCY、バッチ 1、逐次 | 862 / 1,340 | 2,755 / 3,937 |
| LATENCY、バッチ 6、逐次（PaddleOCR の既定） | 687 / 901 | 3,388 / 4,452 |
| **THROUGHPUT、バッチ 1、最適な request 数（4）で並列** | **548 / 729** | **2,598 / 3,520** |
| THROUGHPUT、バッチ 6、並列 | 615 / 698 | 2,933 / 3,730 |
| THROUGHPUT、バッチ 1、8 request で並列 | 570 / 702 | 2,520 / 3,465 |

- 3 番目の設定（太字）を `ov`（主な比較対象）とした。
- 1 番目の設定を `ov-latency`（OpenVINO の素の使い方）として、あわせて計測した。
- 本クレートでも、バッチ 1 が最速であることを確かめた（v6 small、搭乗券）。
  - バッチ 1: 1,209 ms
  - バッチ 6: 2,348 ms

## ボトルネック分析

### 1. 差の大部分は検出の推論から来ている

パイプライン全体の差のうち、検出の推論と認識の推論の差が占める割合（ウォームアップ後の中央値から計算）:

| Model | 画像 | 全体の差 | det 推論の差 | rec 推論の差 |
|---|---|---:|---:|---:|
| small | 搭乗券 | 788 ms | 469 ms（60%） | 344 ms（44%） |
| small | 日本語 | 744 ms | 479 ms（64%） | 276 ms（37%） |
| medium | 搭乗券 | 2,520 ms | 1,653 ms（66%） | 970 ms（38%） |
| medium | 日本語 | 2,572 ms | 1,788 ms（70%） | 782 ms（30%） |
| tiny | 搭乗券 | 306 ms | 258 ms（84%） | 54 ms（18%） |
| tiny | 日本語 | 297 ms | 268 ms（90%） | 32 ms（11%） |

前処理と後処理は共通のコードで、パイプライン全体の 5% 未満である。差にはほとんど関係しない。

検出の推論だけ OpenVINO と同じ速さになったと仮定すると、全体の倍率は次のように縮む。

- small（搭乗券）: 2.35 → 約 1.55
- medium（搭乗券）: 2.02 → 約 1.35

### 2. 検出が遅い理由は、カーネルの効率と並列化の効果の両方にある

| Model | pure 1 → 8 スレッド | OV 1 → 12 スレッド | 1 スレッド同士の倍率 |
|---|---:|---:|---:|
| small | 675 → 525 ms（1.29 倍） | 174 → 88 ms（1.97 倍） | 3.9 倍 |
| medium | 2,805 → 2,167 ms（1.29 倍） | 1,096 → 432 ms（2.54 倍） | 2.6 倍 |
| tiny | 338 → 275 ms（1.23 倍） | 71 → 34 ms（2.08 倍） | 4.8 倍 |

- **カーネルの効率**: 1 スレッド同士でも、本クレートは 2.6〜4.8 倍遅い。
  - モデルが小さいほど差が大きい。tiny と small の検出は、depthwise 畳み込み、要素ごとの演算、Resize や Concat が中心で、計算量に対して行列演算の比率が小さい。
  - tract の高速な経路は行列演算のカーネルで、それ以外の演算子は比較的素直な実装である。OpenVINO（oneDNN）は、畳み込み、BatchNorm、活性化関数を 1 つの JIT カーネルにまとめ、ブロック化したデータ配置で処理する。差が開くのはこの部分だと考えられる。
  - medium は行列演算が多いので、差が 2.6 倍まで縮む。
- **並列化の効果**: tract の並列化は行列演算の中だけで、8 スレッドでも 1.23〜1.29 倍にしかならない（[task-perf-001](task-perf-001-multithread.md) と同じ傾向）。OpenVINO は演算子の中でも空間方向に分割して並列化し、2〜2.5 倍に伸びる。
- `-C target-cpu=native` でビルドしても変わらなかった（v6 small、交互に 3 ラウンド）。
  - 搭乗券: 1,287 → 1,330 ms
  - 日本語: 1,520 → 1,512 ms
  - 検出単体: 485 → 503 ms

  tract の行列演算カーネルは実行時に AVX2 / FMA を選ぶので、コンパイラの設定では差が埋まらない。

### 3. 認識は、バッチ並列のおかげで差が小さい

- 認識モデル単体（バッチ 1）の差は 1 スレッドで 1.4〜1.8 倍、既定のスレッド数で 1.7〜2.8 倍である。
- パイプラインでは、バッチ単位の並列化（task-perf-001）が効いて、認識の推論の差は 1.3〜1.9 倍だった。OpenVINO 自身も、素の `LATENCY` で 1 枚ずつ推論すると、本クレートより遅い（small 日本語: 1,070 ms 対 858 ms）。
- 一方で、バッチ 8 の単体では 3.3〜7.4 倍の差がある。tract はバッチの次元をまたいだ効率化が苦手である。そのため、本クレートの「バッチ 1 にして並列に実行する」という方針は正しい。
- 本クレートの CPU の使い方には余裕がある。平均使用コア数は 3.2〜4.8 で、OpenVINO は 7.1〜10.4。

  スレッド数を変えて追加で計測した結果（v6 small、交互に 3 ラウンド、ミリ秒）:

  | スレッド数 | 合計（搭乗券 / 日本語） | rec 推論 | det 推論 | 平均使用コア数 |
  |---:|---:|---:|---:|---:|
  | 8（既定） | 1,389 / 1,529 | 746 / 834 | 572 / 562 | 4.3 |
  | 12 | 1,404 / 1,502 | 714 / 734 | 614 / 630 | 5.6 |
  | 16 | **1,256 / 1,284** | **636 / 608** | 577 / 570 | 6.3 |

  16 スレッドでは、認識が 15〜27% 速くなり、合計は 10〜16% 縮んだ。検出は変わらない。task-perf-001 で「8 と 16 で差がない」としたのは、行列演算の並列化だけの計測である。バッチを並列に実行する現在の実装では、16 スレッドにも効果がある。

### 4. 初回の実行と、メモリの使い方が逆になっている

- **本クレート**: 入力の形ごとに推論計画をコンパイルする。そのため読み込みは速いが、初回の実行が遅い。
  - 初回とウォームアップ後の差: small 0.9 秒、medium 1.9 秒、tiny 0.5 秒。
  - 認識は幅ごとに計画を作るので、新しい幅の切り出しが来るたびにコンパイルが起きる。
- **OpenVINO**: 動的な形のまま `compile_model` で 1 回だけコンパイルする。初回とウォームアップ後の差は 0.1 秒以下である。
- **メモリ**: 本クレートが少ない。Private のピークは OpenVINO の 27〜58%。
  - OpenVINO は、ストリームごとの作業領域、形ごとのカーネルのキャッシュ、TBB のアロケータでメモリを使う。
  - medium では、本クレートもキャッシュした推論計画（それぞれが重みのコピーを持つ）で 1 GB 程度になり、Working Set のピークは OpenVINO と同じくらいだった。

### 5. CPU 時間の総量はほぼ同じ

1 枚あたりの CPU 時間（実時間 × 平均使用コア数）は、ほぼ同じだった。

| Model | pure | OV |
| :--- | ---: | ---: |
| small | 約 6.2 コア秒 | 約 5.9 コア秒 |
| medium | 約 26 コア秒 | 約 30 コア秒 |
| tiny | 約 1.7 コア秒 | 約 1.6 コア秒 |

- この値はスピン待ちを含むので、目安である。
- 1 スレッドあたりの効率では OpenVINO が上だが、OpenVINO は E コアやハイパースレッディングまで使うので、1 コアあたりの効率は落ちる。
- 結果として、**実時間の差の多くは「同時に何コア使えているか」の差**だと言える。特に検出は、1 回の推論が並列化されないので、その差が大きく出ている。
- 複数の画像を同時に処理する用途（スループット重視）では、本クレートと OpenVINO の差は、実時間の差より小さくなる可能性が高い（未計測）。

### 公式の数値との関係

- OpenVINO の公式値（Xeon 8350C）は small 0.59 秒、medium 1.40 秒である。
- この PC の OpenVINO では、small 0.58〜0.79 秒、medium 2.47〜3.23 秒だった。
- small は同程度だが、medium はモバイル向けの CPU では 2 倍前後遅い。公式の数値とこのクレートの絶対値を直接比べられないことが、改めて確認できた。

## pure-onnx-ocr が OpenVINO に近づくための改善候補

効果が大きいと見込まれる順に並べた。効果は上記の実測からの見積もりである。

| 優先度 | 候補 | 見込める効果 | 根拠 |
| :--- | :--- | :--- | :--- |
| **高** | **検出の並列化（タイル分割）**: 検出の入力を、受容野の分だけ重ねて縦に 2〜4 分割し、それぞれをシングルスレッドの推論で並列に実行して、確率マップを合成する | det 推論 557 → 約 200 ms（small）、全体の倍率 2.35 → 約 1.7 | 認識をバッチ並列にしたとき（task-perf-001）と同じ方法。1 スレッド 675 ms に対し、P コア 4 つでの並列化を想定 |
| **高** | **既定のスレッド数を、論理 CPU 数（上限 16）に引き上げる** | 合計で −10〜16%（実測） | 上記の追加計測。検出には効かない |
| 中 | **tract の検出の演算子をプロファイルする**: `tract ... --profile --cost` などで、depthwise 畳み込み、大きいカーネルの畳み込み、Resize のどれが重いかを特定し、tract 本体へ最適化を提案するか、本クレート側でグラフを書き換える | 1 スレッドで 2.6〜4.8 倍の差を縮める | 1 スレッド同士の比較の結果。行列演算の比率が低い小さいモデルほど差が大きい |
| 中 | **推論計画の事前コンパイル**: 読み込み時やバックグラウンドで、よく使う認識の幅（32 刻み）と、検出の典型的な形の推論計画を作っておく | 初回の実行 −0.5〜1.9 秒 | 初回とウォームアップ後の差。読み込みは OpenVINO より 5〜10 倍速いので、そこに時間を回す余地がある |
| 中 | **複数画像のパイプライン化**: 画像 N の認識と、画像 N+1 の検出を同時に実行する（スループット用の API） | スループットが OpenVINO に近づく | 平均使用コア数が 3〜5 にとどまっている。CPU 時間の総量は同程度 |
| 低 | 認識の幅を量子化する（例: 64 刻み）か、上限を設ける | 計画のキャッシュの再利用率が上がり、メモリと初回の時間が減る | 推論計画のキャッシュで medium が約 1 GB を使っている |
| 効果なし | `-C target-cpu=native` | なし（実測） | tract の行列演算カーネルは、実行時に命令セットを選んでいる |

検出の並列化とスレッド数の変更を組み合わせると、small では OpenVINO の約 1.5 倍、medium では約 1.3 倍まで近づく計算になる。

## 再現手順


## 注意点

- この PC で、この時点に計測した値である。
  - pure の絶対値は、[task-perf-001](task-perf-001-multithread.md) の値より 4〜29% 遅かった。例えば small（搭乗券）は 1,319 → 1,373 ms、medium は 4,558 → 4,986 ms。
  - バックエンドを交互に実行しているので、同じ計測の中での倍率は比較できる。
- OpenVINO の `ov` は、事前のスイープで選んだ最速の設定である。OpenVINO をさらに調整すれば（ストリーム数、スレッドの固定など）、差がもう少し広がる可能性はある。
- 精度は両方とも f32 である。i7-1360P には AMX も AVX-512 もないので、OpenVINO も bf16 を自動では使わない。
- OpenVINO の量子化（INT8）や IR への変換は、使っていない。「同じ ONNX ファイル」という条件を優先したためである。
